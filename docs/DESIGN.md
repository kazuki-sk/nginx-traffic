# 設計

nginx-sitemap の設計と、その理由をまとめる。
使い方は [README](../README.md) を参照。
nginx の挙動の根拠は [spec-basis.md](spec-basis.md) にまとめている。

## 目的と制約

nginx の設定から、リクエストがどこへ流れるかを静的に求める。
次の制約を守る。

- トラフィックは計測しない。アクセスログも読まない。
- nginx の設定を変更しない。reload もしない。
- 常駐しない。timer から起動され、生成したら終了する。
- 1 回の実行で、メモリは 50MB 未満、時間は数秒以内に収める。server が数百ある設定を想定する。
- CGO を使わない、単一の静的バイナリにする。

## 処理の流れ

```
sitemap.conf の読み込み
  → nginx の設定の読み込みと include の展開
  → 設定のハッシュの計算（前回と同じなら終了）
  → 秘密情報のマスク
  → http と stream の解析、変数の評価
  → 手動エントリと注記の反映
  → DNS のスナップショット（resolve on のときだけ）
  → index.html、map.dot、map.json の書き出し
```

各段階は `internal/` の下のパッケージに分けている。
一覧は [development.md](development.md) にある。

## 設定の読み込み

### パーサ

字句解析と構文解析には nginx-go-crossplane を使う。
nginx 社が公開している Go のパーサで、ライセンスは Apache-2.0。
実行時に依存するのは標準ライブラリだけで、CGO も要らない。

crossplane には、ファイルを 1 つずつ解析させる。
include の展開は自前で行う。
crossplane に include を任せると、循環を見つけたときに何も返さずに失敗するため。
自前で展開すれば、循環をエラーとして記録したうえで残りを解析できる。

### 構文エラーからの復旧

crossplane は、構文エラーのあるファイルを丸ごと捨てる。
それではエラーの前にある server も消えてしまう。

そこで、エラーの位置より前のトークンだけで解析し直す。
最後の書きかけの文は捨てる。
開いたままのブロックは閉じる。
行番号は元のファイルと合わせる。

### 意味の検証

crossplane のディレクティブの検査は使わない。
crossplane の知らないディレクティブがあっても、解析を止めないため。
nginx と同じ判定が必要な点は、ツール側で確かめる。
listen のパラメータ、default_server の重複、upstream のポートなどが該当する。

## データモデル

`map.json` の型は `internal/model` にある。
スキーマは、この型から生成する。

### 木の形

listen、server、location、ハンドラ、upstream の順にたどれる。
1 つの server が複数の listen にぶら下がることがある。
そのため、listen は server を ID で参照する。
ハンドラは upstream を名前で参照する。

### すべての要素に付くもの

| 項目 | 内容 |
|---|---|
| `src` | 元になった設定の `ファイル:行` |
| `origin` | `nginx` か `manual` |
| `status` | 値がどこまで決まったか |
| `reasons` | 決まらなかった理由 |

include の経路は、ファイルごとに `files[].included_from` に 1 回だけ書く。
要素ごとに書くと、出力が大きくなりすぎるため。

### 値の表し方

変数を含む値は、次の 4 種類の組み合わせで表す。

| 種類 | 内容 |
|---|---|
| lit | 決まった文字列 |
| sym | 決まらない値。変数名と理由を持つ |
| concat | 値の連結 |
| switch | 条件ごとの値の表 |

`status` はこの形から決める。

| status | 条件 |
|---|---|
| static | 元の値に変数が無い |
| resolved | 変数があったが、lit に畳み込めた |
| conditional | switch が残るが、末端はすべて lit |
| dynamic | sym が残る |
| declared | 手動で書いた値 |

## 変数の評価

実際のリクエストを使わずに、分かる範囲まで値を求める。

### set

rewrite モジュールのディレクティブを、書いた順の命令の並びとして実行する。
server レベルを先に実行し、その結果を location に引き継ぐ。
条件が決まらない `if` の中で `set` した変数は、合流したところで switch にする。
`return` や、常にマッチする `rewrite` に着いたら止める。

### map、geo、split_clients

入力の値が決まっていれば、表から 1 つの値を選ぶ。
決まっていなければ、表をそのまま switch にする。

map の入力が別の map の結果なら、内側の switch の各分岐に外側の map を当てはめる。
こうすると、連鎖した map の結果を、元の入力の条件で表せる。
例えば `$host` から `$tenant`、`$tenant` から `$pool` と引く場合、`$pool` を `$host` の条件で表す。

### 組み込み変数

server の listen から決まるものは決める。
`$server_port` や `$scheme` が該当する。
リクエストや接続で決まるものは sym にする。
どれにも当てはまらない変数は、未知の変数として sym にする。

### 正規表現

Go の `regexp` でコンパイルできる式だけを評価する。
nginx の正規表現は PCRE なので、評価できない式もある。
その場合は推測せず、評価できない理由を付ける。

### 大きさの上限

式の大きさが 256 ノードを超えたら、評価をやめて dynamic にする。
`proxy_pass` の宛先の列挙は 64 件までにする。
大きな map を何段も連鎖させると、組み合わせが爆発するため。

## 出力

### 3 つのファイル

| ファイル | 用途 |
|---|---|
| `map.json` | 機械向け。スキーマ付き |
| `index.html` | 人向け。外部のファイルを読み込まない |
| `map.dot` | Graphviz のグラフ |

グラフは Mermaid ではなく Graphviz にした。
Mermaid は既定で辺が 500 本までで、server が数百ある設定を描けないため。

`index.html` には `map.json` と同じデータを埋め込む。
画面は埋め込んだ JavaScript で描く。
CSP では、埋め込んだスクリプトとスタイルだけを許可する。

### 書き込み

出力先と同じディレクトリに一時ファイルを作り、書き終えてから rename する。
読む側が書きかけのファイルを見ることはない。

`map.json` は最後に置き換える。
`map.json` には設定のハッシュが入っていて、次の実行で再生成するかの判定に使う。
途中で失敗しても、古いハッシュが残るだけで済む。

出力は一時ファイルに直接書き出す。
メモリ上に出力全体を持たないようにするため。

### 設定のハッシュ

次のものから SHA-256 を計算する。

- 読み込んだすべてのファイルのパス、サイズ、内容のハッシュ
- `sitemap.conf` とそこから include したファイル
- ツールのバージョン
- 解析に影響する設定

ハッシュが前回と同じなら、生成を省ける。
`resolve on` のときは省かない。
DNS の結果は、設定が同じでも変わりうるため。

## 手動エントリ

nginx を経由しないサービスも、`sitemap.conf` に書けばマップに載る。

書き方は nginx の設定と同じにした。
同じパーサで読めるので、依存が増えず、行番号も取れる。
YAML も検討したが、ライブラリが 1 つ増えるのでやめた。

手で書いた内容は、nginx から読み取った内容と混ぜない。

- 手で書いた要素には `origin: manual` を付ける。
- `annotate` は注記を足すだけで、nginx 側の値を書き換えない。
- `expect` は宣言として、nginx 側のメンバとは別に持つ。

手で書いた内容は古くなりやすい。
そのため、次の場合に警告を出す。

- 注記の対象が nginx の設定から消えた
- 確認日が古い
- 依存先が無い

## セキュリティ

### 開くファイル

読むのは、メイン設定と include されたファイルだけ。
`ssl_certificate_key` などが指すファイルは開かない。
unit でも、鍵の置き場所を読めなくしている。

### マスク

設定の中に書かれた秘密は、解析の前に伏せる。
伏せた後の値で解析するので、どの出力にも元の値は出ない。
対象は、名前で判定できるヘッダ、ディレクティブ、変数に限る。

### 実行ユーザ

専用の固定ユーザで動かす。
systemd の DynamicUser は使わない。
DynamicUser と StateDirectory を組み合わせると、出力が `/var/lib/private/` の下に置かれる。
このディレクトリは root しか入れないので、nginx のワーカーが出力を読めない。

### unit の制限

書き込めるのは出力先だけにする。
ネットワークは使わない。
システムコールは、一般的なサービスに必要なものだけを許す。
許していない呼び出しは、プロセスを止めずに EPERM で失敗させる。
想定外の呼び出しで、生成の途中に落ちないようにするため。

## 性能

`/usr/bin/time -v` で測った結果。
環境は WSL2 の x86-64。

| 規模 | 時間 | 最大メモリ | map.json |
|---|---|---|---|
| server 300、location 2,100 | 0.31 秒 | 27MB | 1.9MB |
| server 800、location 5,600 | 1.3〜2.2 秒 | 43MB | 5.2MB |
| 同じ設定で生成を省いた場合 | 0.21 秒 | 38MB | — |

最初の実装では、server 800 でメモリが 131MB、`map.json` が 17MB になった。
次の 3 つで減らした。

- `src` を `"ファイル:行"` の文字列にし、include の経路をファイルごとにまとめた。
- `map.json` をインデントなしで書くようにした。
- 出力をメモリにためず、一時ファイルに直接書くようにした。

保険として、Go のヒープの上限を 40MB にしている。

## テスト

設定の fixture を解析し、結果をゴールデンファイルと比べる。
fixture は、実際の nginx の `nginx -t` を通るものだけにする。
通らない設定は、別のディレクトリで扱う。

スキーマは型から生成し、テストで型との一致を確かめる。
すべてのゴールデンが、スキーマに合うことも確かめる。

手順は [development.md](development.md) にある。
